# 04 — Data retrieval and samplesheet

Fetches the 24 selected runs from ENA and writes the nf-core/taxprofiler input
sheet.

- Scripts: `src/download_fastq.py`, `src/build_samplesheet.py`
- Job: `workflow/download.slurm`
- Input: `data/selected_samples.tsv` (see `03_sample_selection.md`)
- Output: 48 FASTQ files on scratch, `data/samplesheet.csv`

```bash
sbatch workflow/download.slurm

python src/build_samplesheet.py \
  --input data/selected_samples.tsv \
  --fastq-dir data/fastq \
  --output data/samplesheet.csv
```

---

## Storage layout

Code lives in the repository under `$HOME`; data lives on scratch. `data/fastq`
is a symlink into the scratch tree, so scripts refer to one stable relative
path while the bytes sit where large files belong.

| Path                              | Holds                          |
|-----------------------------------|--------------------------------|
| `~/infant-gut-shotgun`            | Scripts, docs, configuration   |
| `/scratch/.../nfcore/fastq`       | 48 FASTQ files, 27 GiB         |
| `/scratch/.../nfcore/singularity` | Container images               |
| `/scratch/.../nfcore/work`        | Nextflow intermediate files    |

`NXF_SINGULARITY_CACHEDIR` is exported from `.bashrc` so that container images
land on scratch rather than in the home directory, where the 16S-era cache had
already accumulated 2.4 GB.

Scratch is a shared filesystem under a cleanup policy and was 95% full at the
time of writing. Everything placed there is reconstructible: the FASTQ files
from `selected_samples.tsv`, the container images from the pipeline
definition. Nothing there is treated as an archive.

## Download

### Transport

`fastq_ftp` in the ENA run report gives a scheme-less host path. ENA serves the
same files over FTP, HTTP and HTTPS; the script prepends `https://` because
outbound FTP is filtered on many clusters. A `HEAD` request against the first
file returned `200 OK` before the job was submitted, confirming the choice
without downloading anything.

### One connection at a time

48 files are fetched sequentially. Parallel connections would finish sooner but
add failure modes to a script whose whole job is to move bytes, and ENA is a
public archive that does not need to be saturated for a set this small. The
full transfer took 80 minutes.

### Verification by size

Each file is compared against the byte count in `fastq_bytes` immediately after
it lands, and a mismatch aborts the run. This catches truncated transfers,
which is the failure mode that actually occurs. It does not catch corruption at
matching size — ENA also publishes MD5 sums, which would close that gap, but
quality trimming would surface a corrupt file anyway and the metadata table
does not currently carry the checksum column.

`fastq_bytes` is semicolon-separated, R1 first, matching `fastq_ftp`.

### Resumability

Files already present at full size are skipped, and `wget -c` resumes partial
transfers. An interrupted job can be resubmitted without refetching what is
already on disk.

## Samplesheet

taxprofiler 2.0.1 takes a six-column CSV:

```
sample,run_accession,instrument_platform,fastq_1,fastq_2,fasta
```

`sample` names the biological sample and `run_accession` the sequencing run.
The pipeline concatenates rows sharing a `sample` value when
`--perform_runmerging` is set. Each sample here was sequenced once, so the two
columns hold the same accession and run merging stays off.

`fasta` is for pre-assembled long-read input and is empty, though its
delimiter must still be present.

Paths are absolute and resolve through the symlink to the real scratch
location. The script checks that all 48 files exist before writing the sheet,
so a missing file surfaces here rather than partway through a pipeline run.

`data/samplesheet.csv` is not committed: it encodes absolute paths specific to
this filesystem and is regenerated by the script.
